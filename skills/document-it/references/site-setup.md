# Site setup (Zensical)

**Zensical** is the default site generator. It's the successor to Material for MkDocs, built
by the same team: same look, same Markdown extensions, much faster builds, native TOML
config. Material for MkDocs is in maintenance mode and MkDocs 1.x is no longer maintained
upstream, so new projects shouldn't start on them.

Exception: **versioned docs** (one site per release). `mike` doesn't support Zensical yet,
so use the fallback in `$SKILL/templates/mkdocs-legacy/` (ProperDocs + Material + mike); see
`publishing.md`. Everything in `docs/` is identical for both stacks.

## Files to place in the target repo

| From `$SKILL/` | To repo | Edit |
|---|---|---|
| `templates/zensical.toml` | `zensical.toml` | `site_name`, `site_description`, `site_url`, `repo_url`, `repo_name`, `nav`, mkdocstrings `paths`, api-autonav `modules` |
| `templates/requirements-docs.txt` | `requirements-docs.txt` | add anything you enable |
| `templates/docs/**` | `docs/**` | landing pages, `reference/index.md` API link, `.doc-spec.yml` |
| `scripts/gen_diagrams.py` | `tools/docs/gen_diagrams.py` | nothing (auto-detects `src/` vs flat layout) |
| `scripts/check_drift.py` | `tools/docs/check_drift.py` | nothing |
| `templates/tests/test_docs.py` | `tests/test_docs.py` | Python + pytest projects only |

Add to `.gitignore`: `site/` and `.cache/` (Zensical's build cache).

If the repo uses `uv` / dependency groups, put the requirements in `pyproject.toml`
(`[dependency-groups] docs = [...]`) and change workflow install steps to `uv sync --group docs`.

If the repo already has an `mkdocs.yml`, Zensical can build it directly
(`zensical build -f mkdocs.yml`), but plugins outside Zensical's supported list are silently
ignored (notably `gen-files`, `section-index`). Migrate to `zensical.toml` rather than relying on that.

## Directory layout

```
docs/
├── index.md                 # landing page with quadrant cards
├── .doc-spec.yml            # interview answers (dotfile: not published)
├── tutorials/  index.md, getting-started.md, ...
├── how-to/     index.md, <task>.md, ...
├── reference/
│   ├── index.md             # hand-written: links to API, CLI, config
│   ├── diagrams.md          # tiny markdown-exec block; content generated at build time
│   ├── cli.md               # optional: markdown-exec captures --help
│   ├── config.md            # optional hand-written tables
│   └── api/                 # GENERATED by api-autonav at build time — do not create
├── explanation/ index.md, architecture.md, ...
└── assets/images/
```

## Key zensical.toml pieces (all in the template)

- **Theme features:** tabs, sections, section index pages, back-to-top, footer, breadcrumbs,
  search highlight, code copy/annotations, linked tabs, edit button; light/dark palette toggle.
- **Mermaid:** `pymdownx.superfences.custom_fences` with a `mermaid` fence — rendered natively and themed for dark mode.
- **Snippets:** `pymdownx.snippets` with `base_path = [".", "docs"]` and `check_paths = true`
  (a missing included file fails the build — that's what you want).
- **API autogen:** `[project.plugins.api-autonav]` with `modules = ["src/<pkg>"]` creates one page
  per public module under `reference/api/<pkg>/…` and adds an **API** section to the nav under
  Reference. `mkdocstrings` (Python handler, static analysis via griffe — your code is never
  imported) renders them. `exclude_private = true` drops `_private` modules.
  The API landing page is `reference/api/<pkg>/index.md` — link to that (there's no `api/index.md`).
- **Build-time code:** `[project.plugins.markdown-exec]` runs ```` ```python exec="on" ```` and
  ```` ```bash exec="on" ```` blocks during the build and inserts their output. Used for the
  diagrams page and CLI help. Only for trusted repo code — it executes during every build.

## Nav

Explicit nav keeps the quadrants in order. Don't list API pages — api-autonav adds them.

```toml
nav = [
  { "Home" = "index.md" },
  { "Tutorials" = ["tutorials/index.md", { "Getting started" = "tutorials/getting-started.md" }] },
  { "How-to guides" = ["how-to/index.md", { "Configure authentication" = "how-to/configure-auth.md" }] },
  { "Reference" = ["reference/index.md", { "CLI" = "reference/cli.md" }, { "Diagrams" = "reference/diagrams.md" }] },
  { "Explanation" = ["explanation/index.md", { "Architecture" = "explanation/architecture.md" }] },
]
```

## mkdocstrings options

In the template: `docstring_style = "google"` (switch to `numpy`/`sphinx` to match the
codebase), `show_source`, `show_root_heading`, `show_signature_annotations`,
`separate_signature`, `merge_init_into_class`, `members_order = "source"`, `filters = ["!^_"]`.
Cross-reference any object from prose with `[Client][mypkg.Client]` — a strict build fails if it
no longer exists, which is how renamed APIs get caught.

## Generated diagrams knobs

`docs/reference/diagrams.md` calls `gen_diagrams.render_from_env()`, which reads env vars (set
them in the workflow `env:` if the defaults don't fit):

| Var | Default | Meaning |
|---|---|---|
| `DOCS_SRC` | `src` if it exists, else `.` | Directory containing the top-level packages |
| `DOCS_PACKAGES` | all packages found | Comma-separated top-level packages to diagram |
| `DOCS_EXCLUDE` | `tests,test,docs,tools,examples,scripts,benchmarks` | Top-level names to skip |
| `DOCS_INCLUDE_PRIVATE` | `0` | `1` to include `_private` modules |
| `DOCS_DIAGRAM_MAX_NODES` | `40` | Collapse larger graphs to package level |

With Graphviz `dot` on PATH, diagrams are inline SVG; otherwise Mermaid.

## CLI reference

Any CLI — capture `--help` at build time (the package must be installed in the docs
environment, so uncomment the `pip install -e .` line in each workflow's install step):

````markdown
```bash exec="on" result="text"
mypkg --help
```
````

Add one block per subcommand (`mypkg sync --help`). Introduce each with a sentence.

## Non-Python projects

mkdocstrings/api-autonav are Python-first. For other stacks keep Zensical and generate Markdown
into `docs/reference/` in a CI step **before** `zensical build` (gitignore those paths):
- TypeScript: `typedoc --plugin typedoc-plugin-markdown --out docs/reference/api`
- Go: `gomarkdoc ./... > docs/reference/api.md`
- OpenAPI: render the spec to Markdown (e.g. `widdershins`) or link a hosted Swagger UI
- Rust: link out to docs.rs and hand-write a summary reference page
Diagrams: emit Mermaid/DOT with a language tool (`madge`, `cargo modules`, `go mod graph`) from a
markdown-exec block, the same way `diagrams.md` calls `gen_diagrams.py`.

## Build cache gotcha

Zensical caches rendered pages keyed on their content. Pages whose output comes from code
execution (diagrams, CLI help) don't change textually when the code does, so an incremental
local build can show stale output. **Always build with `--clean` for verification and in CI**
(fresh CI checkouts have no cache anyway). API pages refresh correctly either way.

## Local preview

```bash
pip install -r requirements-docs.txt
zensical serve                   # http://localhost:8000, live reload
zensical build --clean --strict  # what CI runs; must report "No issues found"
```
